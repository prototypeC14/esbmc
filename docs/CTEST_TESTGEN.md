# C CTest Test Case Generation

## Overview

ESBMC supports automatic generation of CTest test cases for C programs. This feature uses symbolic execution and SMT solving to automatically discover test inputs that achieve high code coverage, outputting ready-to-compile test cases compatible with CMake's CTest framework.

**Implementation Note**: The CTest generator reuses ESBMC's existing symbolic execution engine and the same nondet value collection logic as the TestComp XML generator (`--generate-testcase`). The CTest-specific code only handles formatting output as C source files instead of XML.

## Usage

### Basic Command

```bash
# Generate test case for a single counterexample
esbmc program.c --generate-ctest-testcase

# Generate multiple test cases (branch coverage mode)
esbmc program.c --branch-coverage --generate-ctest-testcase
```

This will generate:
- `test_case.c` (or `test_case_1.c`, `test_case_2.c`, ...) - Test case implementations
- `CMakeLists.txt` - CMake build configuration

### Input Format

Your C code should use `__VERIFIER_nondet_*()` functions to mark symbolic inputs:

```c
// example.c
#include <assert.h>

extern int __VERIFIER_nondet_int(void);

int divide(int a, int b) {
    assert(b != 0);  // Safety property
    return a / b;
}

int main(void) {
    int x = __VERIFIER_nondet_int();
    int y = __VERIFIER_nondet_int();

    int result = divide(x, y);
    return 0;
}
```

### Output Format

ESBMC will generate test case implementations:

**test_case.c**:
```c
// Auto-generated by ESBMC v7.x
// This file provides concrete implementations of __VERIFIER_nondet_* functions

int __VERIFIER_nondet_int(void) {
  static int i = 0;
  static const int v[] = { 10, 0 };  // x=10, y=0 (triggers assertion)
  return v[i++];
}
```

**CMakeLists.txt**:
```cmake
# Auto-generated by ESBMC v7.x
cmake_minimum_required(VERSION 3.10)
project(ESBMCGeneratedTests C)

enable_testing()

option(ENABLE_COVERAGE "Enable coverage reporting" OFF)
if(ENABLE_COVERAGE AND CMAKE_C_COMPILER_ID MATCHES "GNU|Clang")
  add_compile_options(-O0 -g --coverage)
  add_link_options(--coverage)
endif()

# Test case compiled with original source + nondet implementation
add_executable(test_case example.c test_case.c)
add_test(NAME test_case COMMAND test_case)
```

### Compiling and Running Tests

**Step 1: Build tests**
```bash
mkdir build && cd build
cmake ..
cmake --build .
```

**Step 2: Run tests**
```bash
ctest --output-on-failure
```

**Step 3: Run with coverage (optional)**
```bash
# Re-configure with coverage enabled
cd build
cmake -DENABLE_COVERAGE=ON ..
cmake --build .
ctest

# Generate coverage report (using gcovr)
gcovr -r .. --branches --html --html-details -o coverage.html

# Or using lcov
lcov --capture --directory . --output-file coverage.info
genhtml coverage.info --output-directory coverage_html
```

## Supported Types

The CTest generator can format all types supported by ESBMC's symbolic execution engine. These types are collected using the same logic as `--generate-testcase` (TestComp XML format) and then formatted as C code.

**Note**: Type support is provided by ESBMC's core engine, not the CTest generator itself. The CTest generator only handles formatting.

### Integer Types
| Function | C Type | Example Values |
|----------|--------|----------------|
| `__VERIFIER_nondet_int()` | `int` | `-10, 0, 127` |
| `__VERIFIER_nondet_uint()` | `unsigned int` | `0, 255, 1000` |
| `__VERIFIER_nondet_char()` | `char` | `-128, 0, 127` |
| `__VERIFIER_nondet_uchar()` | `unsigned char` | `0, 255` |
| `__VERIFIER_nondet_short()` | `short` | `-32768, 0, 32767` |
| `__VERIFIER_nondet_ushort()` | `unsigned short` | `0, 65535` |
| `__VERIFIER_nondet_long()` | `long long` | `-2147483648, 0` |
| `__VERIFIER_nondet_ulong()` | `unsigned long long` | `0, 4294967295` |

### Floating-Point Types
| Function | C Type | Example Values |
|----------|--------|----------------|
| `__VERIFIER_nondet_float()` | `float` | `0.0, 3.14, -1.5` |
| `__VERIFIER_nondet_double()` | `double` | `0.0, 2.718281828` |

### Boolean Type
| Function | C Type | Standard | Example Values |
|----------|--------|----------|----------------|
| `__VERIFIER_nondet_bool()` | `_Bool` | C99/SV-COMP | `0, 1` |

**Important**: The boolean type uses C99's `_Bool` type per SV-COMP standard, not `int`.

## Example: Multiple Types

```c
// mixed_types.c
#include <stdio.h>

extern int __VERIFIER_nondet_int(void);
extern float __VERIFIER_nondet_float(void);
extern _Bool __VERIFIER_nondet_bool(void);

int main(void) {
    int count = __VERIFIER_nondet_int();
    float price = __VERIFIER_nondet_float();
    _Bool is_valid = __VERIFIER_nondet_bool();

    if (is_valid && count > 0 && price > 0.0f) {
        printf("Total: %.2f\n", count * price);
        return 0;
    }
    return 1;
}
```

**Generated test_case.c**:
```c
int __VERIFIER_nondet_int(void) {
  static int i = 0;
  static const int v[] = { 5 };
  return v[i++];
}

float __VERIFIER_nondet_float(void) {
  static int i = 0;
  static const float v[] = { 9.99 };
  return v[i++];
}

_Bool __VERIFIER_nondet_bool(void) {
  static int i = 0;
  static const _Bool v[] = { 1 };
  return v[i++];
}
```

## How It Works

1. **Symbolic Execution**: ESBMC's core engine translates your C code to an internal SSA (Static Single Assignment) representation and performs symbolic execution (supports all `__VERIFIER_nondet_*` types)
2. **SMT Solving**: The SMT solver finds concrete values for the symbolic inputs
3. **Nondet Collection**: Uses `collect_nondet_values()` - the **same shared logic** as `--generate-testcase` (TestComp XML format)
4. **Type Formatting**: CTest generator maps types to C syntax (e.g., `is_bool_type` → `_Bool`, `is_floatbv_type(32)` → `float`)
5. **Code Generation**: Values are formatted as static arrays in `__VERIFIER_nondet_*()` function implementations
6. **Build Configuration**: A `CMakeLists.txt` is generated to compile original source + test implementations
7. **Execution**: CTest runs each test executable and reports results

**Key Point**: The CTest generator does **not** implement type support itself. It reuses ESBMC's existing symbolic execution capabilities and the same collection logic as TestComp XML generation.

### Architecture

```
┌─────────────────────────────────────────────────────────────┐
│ ESBMC Core (Symbolic Execution Engine)                      │
│ • Supports all __VERIFIER_nondet_* types                    │
│ • SSA transformation & SMT solving                          │
└────────────┬────────────────────────────────────────────────┘
             │
             ├──> --generate-testcase (TestComp XML)
             │         │
             │         └─> generate_testcase()
             │                  │
             ├──────────────────┴─> collect_nondet_values() ◄───┐
             │                      [SHARED LOGIC]              │
             │                                                  │
             └──> --generate-ctest-testcase                    │
                       │                                        │
                       └─> ctest_generator::collect() ─────────┘
                                  │
                                  ├─> type_to_c_string()
                                  ├─> format_c_value()
                                  │
                                  v
                           test_case_N.c
                           CMakeLists.txt
                                  │
                                  v
                           CMake + CTest
                                  │
                                  └─> gcov/gcovr
```

**Legend**:
- **ESBMC Core**: Provides type support via symbolic execution
- **Shared Logic**: `collect_nondet_values()` used by both TestComp and CTest
- **CTest Generator**: Only handles C code formatting

## Comparison with Other Test Generators

| Feature | CTest (C) | pytest (Python) | TestComp (XML) |
|---------|-----------|-----------------|----------------|
| **Input** | C + `__VERIFIER_nondet_*` | Python + `__VERIFIER_nondet_*` | C + `__VERIFIER_nondet_*` |
| **Output** | C source files | Python test files | XML files |
| **Build System** | CMake | N/A | Test-Comp harness |
| **Test Runner** | CTest | pytest | Test-Comp tools |
| **Coverage Tool** | gcov/gcovr/lcov | pytest-cov | Test-Comp coverage |
| **Standard** | SV-COMP API | Custom | SV-COMP Test-Comp |
| **Compilation** | Required ✅ | Not needed ❌ | Required ✅ |

## Benefits

✅ **Standards-Compliant**: Uses SV-COMP standard `__VERIFIER_*` API
✅ **Code Reuse**: Shares collection logic with TestComp XML generation - guaranteed consistency
✅ **Coverage-Ready**: Built-in support for gcov coverage analysis
✅ **CMake Integration**: Works seamlessly with existing CMake projects
✅ **Reproducible**: Generated tests are standalone C files
✅ **CI/CD Friendly**: Easy integration with continuous integration pipelines
✅ **Multi-Platform**: Works on Linux, macOS, Windows (with appropriate tools)
✅ **Type Complete**: Supports all types handled by ESBMC's symbolic execution engine

## Limitations

- Requires C99-compliant compiler (for `_Bool` type)
- Currently only supports scalar types (no arrays, structs, pointers as nondet values)
- Each test case is independent (no test dependencies)
- Coverage requires GCC or Clang with `--coverage` support

## Advanced Usage

```cmake

# Link libraries
target_link_libraries(test_case m pthread)
```

```bash
# Run tests in parallel (4 jobs)

# Run specific tests
ctest -R test_case_1
```

## Troubleshooting

### Issue: "cmake: command not found"
**Solution**: Install CMake (see Dependencies section)

### Issue: "error: unknown type name '_Bool'"
**Solution**: Use C99 standard: `gcc -std=c99 ...` or ensure your compiler supports C99

### Issue: "gcov: command not found"
**Solution**: Install GCC or use compiler-specific coverage tools (e.g., `llvm-cov` for Clang)

### Issue: Coverage data not generated
**Solution**:
1. Ensure you configured with `-DENABLE_COVERAGE=ON`
2. Run tests at least once: `ctest`
3. Check for `.gcda` files in build directory

### Issue: Multiple definitions of `__VERIFIER_nondet_*`
**Solution**: Don't link multiple test case files together. Each test case should be compiled separately with the original source.
